## 1 · Múltipla escolha · C1 Projeto, app, rotas e configuração · com código

Com essas rotas, o que acontece quando o navegador pede `/imagem/7/`?

```python
# setup/urls.py
urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('galeria.urls')),
]
```

```python
# galeria/urls.py
from django.urls import path
from galeria.views import index, imagem

urlpatterns = [
    path('', index, name='index'),
    path('imagem/<int:foto_id>/', imagem, name='imagem'),
]
```

- **A)** A view `imagem` responde, recebendo `request` e `foto_id` com o valor inteiro `7`.
- **B)** A view `index` responde, porque o `path('')` casa com qualquer URL que chegue na app.
- **C)** Nenhuma view responde: a rota `imagem/<int:foto_id>/` também precisaria ser
  declarada em `setup/urls.py`.
- **D)** A view `imagem` responde, mas recebe `foto_id` como o texto `'7'`: `<int:...>`
  apenas verifica se o trecho é numérico.

**Gabarito: A.** O `include` repassa o resto do caminho, e o conversor `<int:...>` entrega o
valor já convertido.
**B** confunde rota vazia com coringa; **C** é a ideia de deixar tudo no arquivo do projeto;
**D** reduz o conversor a uma validação.

## 4 · Múltipla escolha · C2 Templates sem duplicação · com código

A página `/` carrega sem erro nenhum, mas nenhuma fotografia aparece, mesmo havendo
registros no banco. Por quê?

```python
# galeria/views.py
def index(request):
    fotografias = Fotografia.objects.all()
    return render(request, 'galeria/index.html', {'cards': fotografias})
```

```django
{# galeria/index.html #}
{% for foto in fotografias %}
  <h2>{{ foto.nome }}</h2>
{% endfor %}
```

- **A)** O contexto publicou a lista sob o nome `cards`, e o template percorre
  `fotografias`, que não existe no contexto — o `for` não roda nenhuma vez.
- **B)** Falta `{% load static %}` no topo do template.
- **C)** `objects.all()` só funciona dentro do Admin; em uma view é preciso usar `filter()`.
- **D)** O contexto precisa receber uma lista, não um QuerySet: sem `list(fotografias)` o
  `for` do template não percorre nada.

**Gabarito: A.** No template vale o nome da **chave** do contexto, não o da variável da view.
**B** trata de arquivos estáticos; **C** inventa uma restrição do ORM; **D** supõe que o
template não itera QuerySet — ele itera.

Neste model, dois campos estão com o tipo errado para o dado que guardam. Quais são, e o que

```python
class Fotografia(models.Model):
    nome = models.CharField(max_length=100)
    legenda = models.CharField(max_length=150)
    data_registro = models.CharField(max_length=20)
    foto = models.CharField(max_length=200)
```

- **A)** `data_registro`, que deveria ser `DateField`, e `foto`, que deveria ser

- **B)** `nome`, que deveria ser `TextField`, e `legenda`, que deveria ser `CharField` sem

**Gabarito: A.** O tipo do campo define o que o banco aceita, como o Django valida o

**B** troca campos corretos; **C** é o erro de usar `CharField` para tudo; **D** guarda o

## 8 · Múltipla escolha · C3 Models e migrações · com código

A busca por `nebu` não encontra a fotografia chamada "Nebulosa de Órion", embora ela esteja
cadastrada. Qual correção resolve?

```python
def buscar(request):
    termo = request.GET.get('buscar')
    fotografias = Fotografia.objects.filter(nome=termo)
    return render(request, 'galeria/buscar.html', {'cards': fotografias})
```

- **A)** Usar `filter(nome__icontains=termo)`: `nome=termo` exige que o nome seja exatamente
  igual ao termo digitado.
- **B)** Percorrer `Fotografia.objects.all()` com um `for` e comparar `foto.nome == termo`
  dentro do laço.
- **C)** Trocar `filter` por `get`, que é o método que faz busca por parte do texto.
- **D)** Rodar `makemigrations` e `migrate`, porque o índice de busca do campo `nome` ainda
  não foi criado.

**Gabarito: A.** `__icontains` busca conteúdo parcial, sem diferenciar maiúsculas de
minúsculas.
**B** é comparar com `==` em vez de usar o ORM (e traria o banco todo para a memória);
**C** inverte o papel de `get`; **D** confunde busca com estrutura de banco.

## 12 · Múltipla escolha · C5 Formulários e validação · com código

Ao enviar o formulário, a aplicação quebra com
`AttributeError: 'FotografiaForms' object has no attribute 'cleaned_data'`. Qual é a causa?

```python
def nova_foto(request):
    form = FotografiaForms(request.POST, request.FILES)
    nome = form.cleaned_data['nome']
    if form.is_valid():
        form.save()
    return redirect('index')
```

- **A)** `cleaned_data` só passa a existir depois de `is_valid()` rodar; a leitura precisa ir
  para dentro do `if`.
- **B)** Falta o `{% csrf_token %}` no template do formulário.
- **C)** O formulário não guarda os dados enviados: o nome tem de ser lido direto de
  `request.POST['nome']`.
- **D)** A validação do campo precisa estar em um método chamado `validar_nome()`; fora desse
  nome, o Django não preenche `cleaned_data`.

**Gabarito: A.** É `is_valid()` que roda as validações e monta `cleaned_data`.
**B** causaria erro 403 no envio, não esse `AttributeError`; **C** é ler `request.POST` direto
e salvar sem validar; **D** erra o padrão, que é `clean_<campo>`.

## 18 · Múltipla escolha · C7 CRUD no fluxo MTV · com código

Ao salvar a edição de uma fotografia, aparece uma fotografia **nova** na galeria e a original
continua igual; além disso, atualizar a página reenvia o formulário. Qual correção resolve os
dois problemas?

```python
def editar_foto(request, foto_id):
    fotografia = Fotografia.objects.get(pk=foto_id)
    form = FotografiaForms(request.POST, request.FILES)
    if form.is_valid():
        form.save()
    return render(request, 'galeria/editar_foto.html', {'form': form})
```

- **A)** Passar o registro ao formulário com
  `FotografiaForms(request.POST, request.FILES, instance=fotografia)` e, depois de salvar,
  devolver `redirect('index')` em vez de `render`.
- **B)** Chamar `fotografia.save()` antes de `form.save()`, para que o Django saiba qual
  registro atualizar.
- **C)** Apagar o registro antigo com `fotografia.delete()` e deixar o `form.save()` criar o
  substituto.
- **D)** Trocar `get(pk=foto_id)` por `filter(pk=foto_id)`, porque `get` devolve uma cópia do
  registro, e não ele mesmo.

**Gabarito: A.** Sem `instance`, o formulário cria um registro novo; e responder a um POST
com `render` faz o recarregamento repetir o envio.
**B** salva o registro inalterado; **C** perde o `pk` original; **D** confunde o retorno de
`get` com o de `filter`.
