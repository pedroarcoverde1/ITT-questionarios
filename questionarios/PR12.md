## 1 · Múltipla escolha · C1 PEP 8 e código idiomático · com código

Quais convenções da PEP 8 este trecho viola, e como corrigi-las?

```python
class pedido_lanchonete:
    def CalcularTotal(self, Itens):
        T = 0
        for i in Itens:
            T += i['preco']
        return T
```

- **A)** A classe deveria ser `PedidoLanchonete` (CapWords) e o método `calcular_total`
  (snake_case); `Itens` deveria ser `itens` e `T` deveria ter um nome que diz o que guarda,
  como `total`.
- **B)** A classe deveria ser `PEDIDO_LANCHONETE`, e `CalcularTotal` já está no padrão de
  métodos.
- **C)** Nenhuma: a PEP 8 não é obrigatória para o interpretador, então se o código roda ele
  está dentro do padrão.
- **D)** Apenas o nome `T`, porque nomes de uma letra são proibidos; classe em snake_case e
  método em CamelCase estão corretos.

**Gabarito: A.** **B** usa o padrão de constantes para classe; **C** confunde "não quebra o
programa" com "está bem escrito"; **D** troca as convenções de classe e de método.

## 5 · Múltipla escolha · C2 Docstrings e type hints · com código

Qual crítica a esta docstring é correta?

```python
def aplicar_desconto(preco: float, percentual: float) -> float:
    """aplicar desconto"""
    return preco - (preco * percentual / 100)
```

- **A)** Ela só repete o nome da função. Precisa dizer o que a função faz, o que cada
  parâmetro significa — `percentual` em pontos percentuais, não em fração — e o que é
  devolvido.
- **B)** Está adequada: com os type hints na assinatura, descrever os parâmetros seria
  redundante.
- **C)** O problema é usar três aspas: docstring de uma linha deve ser escrita como
  comentário com `#`.
- **D)** A docstring deveria repetir o corpo da função em palavras, linha por linha.

**Gabarito: A.** Veja que `aplicar_desconto(50, 150)` é ambíguo sem a docstring — a anotação
`float` não diz se o valor é `20` ou `0.2`.
**B** confunde tipo com significado; **C** inverte comentário e docstring; **D** é comentar o
óbvio em vez de documentar o contrato.

## 7 · Múltipla escolha · C3 Módulos e tratamento de erros · com código

Quais são os problemas desta função, e qual é a correção?

```python
def ler_preco(dados, chave):
    try:
        return float(dados[chave])
    except Exception:
        pass
```

- **A)** O `except Exception` captura qualquer erro e o `pass` esconde a falha: a função
  devolve `None` em silêncio, tanto para chave ausente quanto para valor inválido. O certo é
  capturar `KeyError` e `ValueError` e tratar (ou deixar subir) cada caso.
- **B)** O problema é só o `float()`: deveria ser `int()`, e aí o `except` seria
  desnecessário.
- **C)** O problema é não haver `finally`; com ele, o `pass` passa a ser aceitável.
- **D)** Nenhum: capturar `Exception` é a prática recomendada, porque garante que a função
  nunca quebra.

**Gabarito: A.** Quem chamou não tem como distinguir "não existe" de "existe mas é inválido",
e o programa segue com `None` em estado inválido.
**B** troca o tipo de conversão e ignora o `pass`; **C** acrescenta um bloco que não trata
nada; **D** é exatamente o erro de esconder a falha.

## 10 · Múltipla escolha · C4 Princípios SOLID · com código

Qual princípio esta classe viola, e qual correção resolve?

```python
class Pedido:
    def __init__(self, itens):
        self.itens = itens

    def calcular_total(self): ...
    def salvar_no_banco(self): ...
    def enviar_email_confirmacao(self): ...
    def gerar_pdf_do_recibo(self): ...
```

- **D)** A responsabilidade única, e a correção é dividir em quatro classes de um método cada,

**Gabarito: A.** São quatro motivos diferentes para a classe mudar — e quatro são demais.
**B** troca o princípio e propõe o oposto da correção; **C** confunde "falar do mesmo assunto"
com "ter uma responsabilidade"; **D** acerta o princípio e erra a leitura dele.

## 14 · Múltipla escolha · C5 Design patterns essenciais · com código

Qual padrão está em uso aqui, e o que ele permite?

```python
class Pedido:
    def __init__(self, calculo_frete):
        self.calculo_frete = calculo_frete

    def total(self, itens):
        return sum(itens) + self.calculo_frete.calcular(itens)
```

- **A)** **Strategy**: o algoritmo de frete é injetado como objeto, então trocar a regra é
  passar outro objeto no construtor, sem alterar `Pedido`.
- **B)** **Template Method**: `Pedido` define o esqueleto do cálculo e as subclasses
  sobrescrevem o passo do frete.
- **C)** **Factory Method**: `Pedido` cria o objeto de frete conforme a entrada recebida.
- **D)** **Observer**: o objeto de frete é notificado sempre que o total muda.

**Gabarito: A.** **B** é o padrão vizinho — ele usaria herança e sobrescrita, não injeção;
**C** criaria o objeto em vez de recebê-lo; **D** não há evento nem interessados aqui.

## 17 · Múltipla escolha · C6 Testes unitários com Pytest · com código

Qual é o problema deste teste?

```python
def calcular_total(itens):
    return sum(item['preco'] * item['qtd'] for item in itens)


def test_calcular_total():
    itens = [{'preco': 10, 'qtd': 2}, {'preco': 5, 'qtd': 1}]
```

- **C)** Falta um `print()` para conferir o resultado na saída do pytest.
- **D)** O nome está errado: deveria começar com `verificar_` em vez de `test_`.

**Gabarito: A.** Sem `assert`, o teste só verifica que a função não quebra — se ela devolver
`0`, `None` ou qualquer valor errado, ele continua verde.
**B** confunde "não levanta erro" com "está correto"; **C** confunde inspeção manual com
asserção; **D** é o prefixo que o pytest exige.

## 18 · Múltipla escolha · C6 Testes unitários com Pytest · com código

Qual é o problema deste teste, e qual é a correção?

```python
def aplicar_desconto(preco, percentual):
    if percentual > 100:
        raise ValueError('percentual acima de 100')
    return preco - (preco * percentual / 100)


def test_desconto_acima_de_cem():
    try:
        aplicar_desconto(50, 150)
    except ValueError:
        pass
```

- **A)** O teste continua passando se a função **deixar** de levantar o erro, porque nada é
  afirmado. O certo é `with pytest.raises(ValueError): aplicar_desconto(50, 150)`.
- **B)** Está correto: capturar a exceção com `try/except` é a forma recomendada de testar
  erro no pytest.
- **C)** O problema é o tipo: deveria ser `except Exception`, para capturar qualquer erro que
  a função lance.
- **D)** O teste verifica dois comportamentos ao mesmo tempo e deveria ser dividido em dois.

**Gabarito: A.** Se alguém apagar o `raise`, a chamada passa sem exceção, o `try` termina e o
teste fica verde — testando nada.
**B** é o erro de usar `try/except` no lugar de `pytest.raises`; **C** amplia a captura e
piora; **D** descreve um problema que não está neste teste.

## 19 · Múltipla escolha · C6 Testes unitários com Pytest

O que o nome e a estrutura de um teste precisam comunicar a quem o lê?

- **C)** O corpo deve verificar o maior número possível de comportamentos, para reduzir a

- **D)** O nome deve repetir o nome da função testada, e o corpo deve cobrir todos os

**Gabarito: A.** **B** apaga a informação do nome e supõe dependência de ordem; **C** e **D**
juntam comportamentos e, quando falham, não dizem qual deles quebrou.

## 20 · Dissertativa · C7 TDD e cobertura de testes

Explique por que, no TDD, o primeiro teste precisa falhar antes de o código existir. Depois,
comente a afirmação: "chegamos a 100% de cobertura, então o código está sem bugs".

**O que a resposta precisa conter:**

1. Os três passos do ciclo, na ordem: escrever o teste que falha, fazer o código passar,

   entradas-limite podem nunca ter sido exercitadas.

**Faixas:** os três pontos = integral · explica o teste que falha mas trata cobertura como
garantia parcial de qualidade = parcial · descreve o ciclo fora de ordem e aceita a afirmação
